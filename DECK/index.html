Editing code that makes things.

DECK studies whether language models can modify executable programs whose correctness lives in the artifact they produce—not only in source code or unit tests. Our first domain is Blender Python and editable 3D geometry.

The project in one minute

A benchmark, a stress test, and an improvement loop.

The core shift is from asking “does the code run?” to asking “did the requested change appear in the compiled artifact, without destroying what should remain?”

01

Artifact-grounded editing

A model receives an existing Blender Python program and a modification instruction. It must return executable code whose rendered 3D output satisfies the edit.

02

Controlled difficulty

Six levels move from literal parameter changes to component logic, topology, semantic restyling, and multi-object scene composition.

03

Feedback-driven recovery

We test whether render observations, checklist signals, and execution errors help the same model repair its own output over multiple rounds.

Evaluation pipeline

Source code to visual evidence.

Every model sees the same source and edit request. We compile, render six canonical views, and evaluate atomic checklist items.

Input Existing script

Editable bpy code reconstructed from real programs.

Task Edit request

Four generated edits at each of six difficulty levels.

Model Code revision

The tested LLM returns a complete modified program.

Item-level satisfaction plus execution status.

What we have learned

Models can improve—measurement is now the bottleneck.

Execution feedback is highly actionable. Quality feedback also helps, but its apparent gain is entangled with the benchmark’s own checklist and judge.

84.77% → 99.77%

Render success after feeding Blender errors back to the original model. 396 of 402 initial failures were repaired, usually within 2–3 rounds.

+0.138

Largest aggregate quality gain: per-item checklist verdicts plus renders, across the nine models that support multimodal feedback.

!

Important validity gap: feedback and final measurement are coupled.

The current checklist feedback comes from the benchmark framework itself—the same task rubric and Sonnet 5 judge family used to score progress. The next design must separate the feedback signal from the final evaluator, add hidden preservation checks, and calibrate against independent or human judgments.
